                        REVISION PRIORITARIA DE SEGURIDAD Y OPTIMIZACION - TELERIN
                        Fecha: 2026-05-18

                        ==================================================
                        1. CRITICO - SESION GUARDANDO EL USUARIO COMPLETO
                        ==================================================

                        Ubicacion principal:
                        - TeleRin_backend/app.py

                        Que pasa:
                        - El backend guarda session["usuario"] = usuario completo.
                        - En Flask, la sesion por defecto se guarda en cookie firmada del lado del cliente.
                        - Eso hace fragil la persistencia y puede producir errores como /api/sesion devolviendo null.

                        Por que es grave:
                        - Ya esta rompiendo funcionalidad real: la barra lateral desaparece porque useSesion() recibe null.
                        - Guardar un objeto completo en sesion es mas fragil que guardar solo un identificador.
                        - Puede desincronizarse con la base de datos.
                        - Hace mas dificil depurar.

                        Que deberia hacerse:
                        - Guardar solo session["codigo_usuario"] o session["correo_usuario"].
                        - Crear una funcion helper tipo obtener_usuario_actual().
                        - Esa funcion deberia leer el identificador desde session y consultar la DB.
                        - /api/sesion y /api/necesita_usuario deberian usar esa funcion.

                        Ventajas:
                        - Sesion mas estable.
                        - Menos bugs raros.
                        - Mejor practica.
                        - Datos siempre frescos desde DB.

                        Desventajas:
                        - Mas consultas a DB.
                        - Pero normalmente el costo es pequeño y vale la pena.

                        Prioridad:
                        - MAXIMA

                        Dificultad:
                        - MEDIA / ALTA
   
==================================================
2. CRITICO - SECRETOS HARDCodeados EN EL CODIGO
==================================================
  
Ubicaciones:
- TeleRin_backend/app.py -> app.secret_key
- TeleRin_backend/app.py -> password de correo
- docker-compose.yml -> credenciales de postgres

Que pasa:
- Hay claves sensibles escritas directamente en el codigo.

Por que es grave:
- Si el repo se comparte o se filtra, se comprometen sesiones, correo y DB.
- No permite rotar secretos facilmente.
- Es mala practica de seguridad.

Que deberia hacerse:
- Mover secret_key, password del correo y credenciales DB a variables de entorno.
- Leer con os.getenv().
- Opcionalmente usar un archivo .env para desarrollo.

Ventajas:
- Mejor seguridad.
- Configuracion mas profesional.
- Facil rotacion de claves.

Desventajas:
- Hay que configurar entorno.
- Puede ser un poco mas trabajo al arrancar el proyecto.

Prioridad:
- MAXIMA

Dificultad:
- BAJA / MEDIA


==================================================
3. CRITICO - FALTA DE PROTECCION CSRF
==================================================

Ubicaciones:
- Multiples rutas POST del backend
- Frontend usa credentials: "include"

Que pasa:
- El sistema usa cookies de sesion.
- Hay POST autenticados.
- No se ve proteccion CSRF explicita.

Por que es grave:
- Un sitio externo podria intentar disparar requests autenticados desde el navegador del usuario.

Que deberia hacerse:
- Implementar CSRF token.
- O minimo endurecer cookies y validar Origin/Referer si no se va a meter una solucion completa.

Ventajas:
- Reduce mucho el riesgo de ataques CSRF.

Desventajas:
- Añade complejidad al flujo frontend-backend.

Prioridad:
- MAXIMA

Dificultad:
- MEDIA

4. ALTA - SQL DINAMICO CON TABLAS/CAMPOS POR STRING
==================================================

Ubicacion:
- TeleRin_backend/app.py
- Funciones tipo dato_en_db, insertar_db, actualizar_datos

Que pasa:
- Los valores parecen parametrizados, pero los nombres de tabla/campo se construyen por string.

Por que importa:
- Si algun nombre llega a estar mal controlado, abre riesgo de SQL injection estructural.
- Hace el codigo mas dificil de auditar.

Que deberia hacerse:
- Limitar tablas y campos a listas blancas.
- O reemplazar helpers genericos por consultas explicitas en zonas sensibles.

Ventajas:
- Menor riesgo.
- Codigo mas claro.

Desventajas:
- Menos “comodidad” que helpers genericos.
- Puede requerir mas codigo repetido.

Prioridad:
- ALTA

- MEDIA

                        ==================================================
                        6. ALTA - DEMASIADAS CONSULTAS REPETIDAS DE SESION/USUARIO
                        ==================================================

                        Ubicaciones:
                        - TeleRin_backend/app.py
                        - actualizar_sesion()
                        - rutas que llaman datos_indefinidos() + actualizar_sesion()

                        Que pasa:
                        - actualizar_sesion hace 2 SELECT del mismo usuario.
                        - varias rutas vuelven a refrescar sesion aunque no siempre hace falta.

                        Por que importa:
                        - Mas carga en DB.
                        - Mas latencia.
                        - Mas complejidad.
                        - Mas riesgo de estados inconsistentes.

                        Que deberia hacerse:
                        - Reducir a un solo SELECT cuando sea posible.
                        - Separar la logica de “normalizar defaults” de la logica de “leer usuario”.
                        - No refrescar sesion completa en cada endpoint si no hace falta.

                        Ventajas:
                        - Mejor rendimiento.
                        - Backend mas limpio.

                        Desventajas:
                        - Requiere revisar varias rutas.

                        Prioridad:
                        - ALTA

                        Dificultad:
                        - MEDIA

7. ALTA - CORS Y COOKIES DEBERIAN ENDURECERSE
==================================================

Ubicacion:
- TeleRin_backend/app.py

Que pasa:
- CORS con supports_credentials=True.
- Permitido para varios origenes locales.
- No se vio configuracion fuerte de cookies tipo Secure/SameSite/HttpOnly mas alla del default.

Por que importa:
- En desarrollo puede estar bien.
- En produccion deberia estar mucho mas cerrado.

Que deberia hacerse:
- Separar configuracion de desarrollo y produccion.
- Revisar SESSION_COOKIE_SECURE.
- Revisar SESSION_COOKIE_SAMESITE.
- Revisar SESSION_COOKIE_HTTPONLY.
- Mantener origins permitidos bien controlados.

Ventajas:
- Mejor seguridad de sesion.

Desventajas:
- Puede complicar pruebas locales si no se configura bien.

Prioridad:
- ALTA

Dificultad:
- MEDIA

==================================================

Ubicaciones:
- /api/iniciar_sesion

- validacion de codigo

Ventajas:
