0. PROPOSITO DE ESTE DOCUMENTO
========================================================================

Este documento explica, con detalle y aplicado al proyecto TeleRin, que
componentes tecnicos conviene tener si la meta es que la plataforma pueda
crecer a gran escala. La idea no es solamente nombrar tecnologias, sino
explicar:

- que es cada cosa
- para que sirve
- por que deberia estar en este proyecto
- en que parte del sistema aparece
- como se veria en la practica
- que problemas evita
- que errores comunes hay que evitar

El objetivo es que este archivo te sirva como mapa tecnico de referencia
para entender como evoluciona una red social moderna desde un backend
simple hasta una plataforma preparada para mucho trafico.

Este documento esta enfocado en TeleRin, que por el contexto del proyecto
parece una aplicacion social con:

- usuarios
- autenticacion
- publicaciones
- historias
- likes
- comentarios
- imagenes
- posiblemente notificaciones
- posiblemente feed o timeline

No todas las piezas tienen que implementarse al mismo tiempo. Algunas
deben existir desde el principio, otras pueden prepararse en diseño y
activarse cuando el trafico lo exija.

1. IDEA CENTRAL: ESCALAR NO SIGNIFICA SOLO USAR UN LENGUAJE RAPIDO
========================================================================

Cuando se habla de soportar millones de usuarios, mucha gente piensa
primero en cambiar de lenguaje o en usar una base de datos NoSQL. Eso es
normal, pero no suele ser la primera decision correcta.

Una aplicacion no escala solo porque:

- use Go
- use Rust
- use Java
- use MongoDB
- use Cassandra

Una aplicacion escala cuando su arquitectura evita cuellos de botella.

Los grandes cuellos de botella en una red social suelen aparecer en:

- consultas de base de datos mal pensadas
- archivos multimedia servidos de forma incorrecta
- trabajo pesado dentro de peticiones HTTP
- feed construido de forma ineficiente
- falta de cache
- falta de workers en segundo plano
- falta de replicas de lectura
- monolito demasiado acoplado
- sesiones o datos guardados en memoria local del proceso
- ausencia de observabilidad

Eso significa que una aplicacion en Python puede soportar muchisimo mas de
lo que parece si:

- el request hace poco trabajo
- la base de datos esta bien modelada
- Redis absorbe lecturas repetidas
- los archivos viven fuera del servidor de aplicacion
- lo pesado corre en segundo plano
- hay varias instancias del backend
- hay estrategia para feed, contadores y notificaciones

Conclusion principal:

No hace falta cambiar de lenguaje solo por miedo al futuro. Hace falta
diseñar un sistema que permita crecer sin romperse.

3. BACKEND PRINCIPAL: QUE ES Y POR QUE IMPORTA
========================================================================

El backend principal es el servicio que recibe las peticiones de cliente,
aplica reglas de negocio, consulta datos y responde.

En TeleRin, ese backend parece estar actualmente en Python con Flask.

Que hace el backend principal:

- registra usuarios
- autentica sesiones
- crea publicaciones
- procesa likes
- guarda comentarios
- responde datos del perfil
- valida permisos
- devuelve informacion al frontend

Por que es importante:

- es el cerebro de la aplicacion
- conecta todas las piezas
- coordina lo que entra y lo que sale
- define reglas de negocio

Que deberia tener un backend de este tipo si se piensa en escalar:

- rutas claras y separadas por dominio
- validaciones robustas
- acceso a base de datos desacoplado
- configuracion por variables de entorno
- seguridad en sesiones o tokens
- integracion con cache
- integracion con workers
- logs estructurados
- codigo modular

Que no deberia hacer:

- procesar imagenes pesadas dentro del request principal
- depender de memoria local para datos importantes
- tener todo el proyecto en un solo archivo enorme
- guardar secretos en el codigo
- servir media pesada desde el mismo contenedor

4. DEBERIAS CAMBIAR DE LENGUAJE
========================================================================

La respuesta seria: no necesariamente.

Lenguajes mas comunes en sistemas grandes:

- Python
- Go
- Java
- Kotlin
- Node.js con TypeScript
- Rust en casos puntuales

Que significa usar otro lenguaje "mas rapido":

- un servicio puede atender mas peticiones por proceso
- la latencia puede bajar en tareas intensivas
- algunos runtimes consumen menos memoria

Pero eso no resuelve por si solo:

- una consulta SQL mala
- una arquitectura mal desacoplada
- un feed mal disenado
- media servida sin CDN
- ausencia de cache
- falta de jobs asincronos

Cuando SI tendria sentido introducir otro lenguaje:

- si una parte muy concreta del sistema requiere altisimo rendimiento
- si necesitas un servicio realtime muy exigente
- si quieres un servicio de fan-out o colas de eventos muy optimizado
- si procesamiento de media o recomendaciones crece mucho

Ejemplos futuros:

- backend principal en Python
- servicio de feed en Go
- servicio de websockets en Go o Node
- servicio de recomendacion en otro stack

Eso si tiene sentido porque cada tecnologia resuelve un problema concreto.

Lo que NO suele tener sentido:

- reescribir todo desde cero solo "porque en el futuro podria crecer"

Para TeleRin:

- Python sigue siendo valido
- la prioridad deberia ser arquitectura, no reescritura completa

5. POR QUE POSTGRESQL DEBERIA ESTAR EN ESTE PROYECTO
========================================================================

PostgreSQL es una base de datos relacional.

Que significa relacional:

- guarda datos estructurados en tablas
- permite relaciones entre entidades
- mantiene integridad entre datos
- permite transacciones confiables

Por que eso importa en una red social:

- un usuario existe y tiene publicaciones
- una publicacion tiene autor
- un comentario pertenece a un post
- un like pertenece a un usuario y a un recurso
- una historia tiene fecha de expiracion
- una relacion follow conecta usuario A con usuario B

PostgreSQL encaja muy bien en ese tipo de datos porque:

- las relaciones importan mucho
- la consistencia importa mucho
- se necesitan indices
- se necesitan joins
- se necesitan restricciones

Ejemplos en TeleRin:

Tabla USUARIOS:
- id
- username
- email
- password_hash
- fecha_creacion

Tabla POSTS:
- id
- autor_id
- texto
- media_url
- fecha_creacion

Tabla LIKES_POST:
- id
- usuario_id
- post_id
- fecha_creacion

Tabla COMENTARIOS:
- id
- post_id
- autor_id
- texto
- fecha_creacion

Tabla HISTORIAS:
- id
- autor_id
- media_url
- fecha_expiracion
- fecha_creacion

Por que deberia estar ya:

- da una base consistente
- te permite crecer con orden
- soporta indices, replicas, particionado y consultas avanzadas
- tiene ecosistema maduro

En que parte lo vas viendo:

- en el codigo del backend
- en las funciones de acceso a datos
- en el esquema de tablas
- en las migraciones
- en las consultas e indices
- en las politicas de lectura y escritura


========================================================================
6. SQL VS NOSQL PARA TELERIN
========================================================================

Esta es una de las preguntas mas frecuentes al construir una red social.

La idea equivocada comun es:

"Si hay likes, comentarios e historias, entonces necesito NoSQL".

No necesariamente.

NoSQL es una familia amplia. No es una sola cosa. Incluye:

- document stores como MongoDB
- key-value stores como Redis
- wide-column stores como Cassandra
- bases distribuidas administradas como DynamoDB

Cada una resuelve problemas distintos.

Por que SQL sigue siendo muy util en una red social:

- usuarios y permisos necesitan consistencia
- relaciones follow/follower son relacionales
- comentarios y likes se consultan con filtros claros
- se necesitan constraints
- se necesita evitar datos huerfanos

Cuando NoSQL puede entrar:

- cache de lectura
- timelines precalculados
- eventos de actividad
- contadores masivos
- almacenamiento documental de ciertos objetos flexibles
- datos que se reparten por enormes volumnes de escritura distribuida

Entonces la respuesta madura es:

- SQL para la verdad principal del negocio
- NoSQL o sistemas especializados para problemas concretos

Que deberia hacer TeleRin:

- mantener PostgreSQL como base principal
- agregar Redis como sistema complementario
- evaluar otros motores solo si un caso real lo exige


========================================================================
7. POR QUE REDIS DEBERIA ESTAR EN TELERIN
========================================================================

Redis es una base de datos en memoria, extremadamente rapida, usada muchas
veces como cache o estructura temporal.

Que significa "en memoria":

- los datos se leen y escriben muy rapido
- es ideal para operaciones frecuentes y pequeñas
- no reemplaza por completo a la base principal

Que problemas resuelve Redis:

- consultas repetidas a la base de datos
- sesiones distribuidas
- rate limiting
- contadores rapidos
- colas simples
- timelines o listas precalculadas
- datos temporales con expiracion

Por que deberia estar en TeleRin:

- una red social repite muchas lecturas
- perfiles y posts populares pueden consultarse miles de veces
- las historias expiran, y Redis maneja TTL muy bien
- las sesiones no deberian depender de un solo proceso
- los contadores de likes o vistas pueden leerse muy seguido

En que partes lo verias:

1. Sesiones
   En lugar de guardar datos importantes en memoria local o en cookies
   demasiado cargadas, Redis puede guardar estado de sesion.

2. Feed cacheado
   Un feed de inicio es caro de armar si en cada request haces multiples
   joins y ordenamientos. Redis puede guardar resultados temporales.

3. Rate limiting
   Si un usuario intenta enviar cientos de likes o comentarios por minuto,
   Redis permite contar intentos y frenarlos.

4. Codigos temporales
   Tokens de recuperacion, verificacion o expiraciones temporales.

Ejemplo conceptual:

- usuario abre inicio
- backend revisa si el feed esta en Redis
- si esta, responde rapido
- si no esta, consulta PostgreSQL, construye feed, lo guarda en Redis y lo
  devuelve

Eso reduce muchisimo carga en la base principal.


========================================================================
8. POR QUE LAS IMAGENES Y VIDEOS NO DEBERIAN VIVIR EN EL MISMO SERVIDOR
========================================================================

Uno de los errores mas comunes en proyectos que luego quieren crecer es
guardar imagenes y videos en el disco local del backend o del contenedor.

Por que eso es un problema:

- si despliegas varias instancias, cada una tiene su propio disco
- si una instancia cae, puede perder acceso a sus archivos locales
- sincronizar archivos entre servidores es complicado
- servir media pesada desde el backend consume recursos innecesarios
- los contenedores no deberian ser tu sistema de almacenamiento permanente

Lo correcto es usar object storage.

Ejemplos:

- Amazon S3
- Cloudflare R2
- Google Cloud Storage
- MinIO si quieres algo compatible en self-hosting

Que es object storage:

- un sistema pensado para guardar archivos binarios
- escalable
- durable
- accesible por URL o API

Por que deberia estar en TeleRin:

- historias probablemente incluyen imagenes o video
- publicaciones pueden incluir media
- perfiles tienen avatar
- media es una de las partes mas pesadas en una red social

En que parte lo vas viendo:

- al subir archivos
- al guardar solo URL o metadata en PostgreSQL
- al servir contenido desde CDN
- al procesar variantes de imagen

Ejemplo recomendado:

En vez de guardar:
- ruta local del archivo dentro del servidor

Guardas:
- object_key
- bucket
- public_url o signed_url
- metadata del archivo


========================================================================
9. QUE ES UNA CDN Y POR QUE DEBERIA EXISTIR
========================================================================

CDN significa Content Delivery Network.

Que hace:

- distribuye archivos desde ubicaciones cercanas al usuario
- reduce latencia
- descarga trafico del backend
- acelera imagenes, videos y archivos estaticos

Por que importa tanto en una red social:

- la experiencia depende mucho de que las imagenes carguen rapido
- el backend no deberia estar dedicado a empujar archivos pesados
- millones de usuarios leyendo media es mucho mas costoso que guardar un
  like o un comentario

Que deberia servir una CDN en TeleRin:

- imagenes de publicaciones
- historias
- fotos de perfil
- videos
- assets estaticos del frontend

Ejemplo de flujo:

1. usuario sube una imagen
2. backend la manda a object storage
3. se procesa si hace falta
4. se publica bajo una URL servida por CDN
5. otros usuarios la descargan desde la CDN, no desde Flask

Beneficio:

- el backend queda libre para logica de negocio


========================================================================
10. COLAS Y WORKERS: POR QUE EL REQUEST NO DEBERIA HACER TODO
========================================================================

Una peticion HTTP deberia responder lo antes posible.

Si dentro del mismo request haces trabajo pesado, aumenta:

- la latencia
- el consumo de CPU
- el tiempo de espera del usuario
- el riesgo de timeout

Para eso existen colas y workers.

Que es una cola:

- un sistema donde dejas una tarea pendiente

Que es un worker:

- un proceso separado que toma tareas de la cola y las ejecuta

Ejemplos de tareas que deberian ir a workers en TeleRin:

- enviar correos de registro
- procesar imagenes
- generar thumbnails
- borrar historias expiradas
- notificaciones push
- generar resumentes o actividad
- fan-out de publicaciones

Tecnologias comunes:

- Celery
- Dramatiq
- RQ
- RabbitMQ o Redis como broker

Ejemplo practico:

Caso malo:
- usuario sube foto
- request valida
- request redimensiona varias versiones
- request guarda todo
- request manda email
- request actualiza feed de cientos de seguidores
- request responde

Eso es muy pesado.

Caso correcto:
- usuario sube foto
- request valida
- request registra la publicacion
- request envia tareas a la cola
- backend responde rapido
- workers procesan lo demas

Por que deberia estar ya en tu diseño:

- porque separar tareas evita reescribir logica luego
- porque el crecimiento natural de una red social genera mucho trabajo
  asincrono


========================================================================
11. ARQUITECTURA STATELESS: QUE ES Y POR QUE IMPORTA
========================================================================

Un backend stateless es uno en el que una instancia no depende de memoria
local para recordar informacion critica del usuario entre peticiones.

Por que esto importa:

- si tienes una sola instancia, da igual
- si tienes 10, 50 o 200 instancias, ya no da igual

Si una aplicacion depende de memoria local:

- una peticion puede funcionar en un servidor y fallar en otro
- el balanceador complica la afinidad
- reiniciar procesos rompe estado

Lo que debe vivir fuera del proceso:

- sesiones compartidas
- cache compartida
- archivos persistentes
- tareas pendientes
- estado durable del negocio

Donde vive cada cosa:

- PostgreSQL: datos permanentes
- Redis: sesiones, cache, temporales
- object storage: archivos
- cola: tareas pendientes

Por que deberia existir en TeleRin:

- porque una red social necesita muchas instancias cuando crece
- porque quieres poder desplegar varias copias del backend sin dolor


========================================================================
12. BALANCEADOR DE CARGA: QUE ES Y DONDE APARECE
========================================================================

El balanceador de carga recibe trafico entrante y lo distribuye entre
varias instancias del backend.

Que problema resuelve:

- evita que un solo servidor reciba todo
- permite escalar horizontalmente
- mejora disponibilidad

Ejemplos:

- Nginx
- HAProxy
- load balancers administrados de cloud

Que verias en la practica:

- varios contenedores del backend
- el balanceador delante de ellos
- health checks para sacar instancias caidas

Por que importa en TeleRin:

- cuando la app crezca no vas a querer depender de una sola instancia
- distribuir trafico es parte basica del escalado


========================================================================
13. ESCALADO HORIZONTAL: COMO SE VE EN UN PROYECTO COMO ESTE
========================================================================

Escalar horizontalmente significa agregar mas instancias del servicio en
lugar de solo hacer una maquina mas grande.

Ejemplo:

En vez de:
- 1 servidor gigantesco

Pasas a:
- 4 instancias del backend
- 1 Redis compartido
- 1 PostgreSQL principal
- 1 balanceador

Ventajas:

- tolerancia a fallos
- despliegues mas seguros
- crecimiento gradual

Para que esto funcione, TeleRin necesita:

- backend stateless
- archivos fuera del contenedor
- sesiones compartidas
- configuracion externa

14. FEED O TIMELINE: EL PROBLEMA TECNICO REAL DE UNA RED SOCIAL
========================================================================

Uno de los componentes mas dificiles de escalar en una red social es el
feed de inicio.

Por que:

- mezcla datos de muchas personas
- necesita orden por tiempo o relevancia
- se consulta muchisimas veces
- puede incluir enriquecimiento de datos
- a veces necesita fan-out a seguidores

No es lo mismo guardar un post que construir el feed de millones.

Problemas comunes de un feed:

- demasiados joins por request
- paginas lentas
- mucha lectura repetida
- ranking costoso
- combinacion de posts, historias y sugerencias

Estrategias comunes:

1. Fan-out on write
   Cuando alguien publica, empujas esa publicacion a feeds precalculados de
   sus seguidores.

2. Fan-out on read
   Cuando el usuario abre inicio, calculas el feed en ese momento.

3. Estrategia hibrida
   Precalculas parte y mezclas otra parte al leer.

Para TeleRin, al principio suele ser suficiente:

- feed cronologico basico
- cache
- paginacion
- indices correctos

Mas adelante:

- precomputacion parcial
- workers
- almacenamiento temporal en Redis

Ejemplo aplicado:

Usuario sigue a 800 cuentas.

Si cada vez que entra haces:
- buscar seguidos
- consultar miles de posts
- ordenar
- cruzar likes y comentarios
- agregar datos del autor

vas a castigar mucho la base.

Mejor opcion futura:

- prearmar bloques del feed
- cachear resultados
- invalidar cache cuando haya nueva actividad relevante

15. HISTORIAS: COMO DEBERIAN PENSARSE
========================================================================

Las historias tienen dos caracteristicas tecnicas importantes:

- media pesada
- expiracion automatica

Eso implica varias decisiones:

1. La media debe vivir en object storage
2. La metadata debe vivir en PostgreSQL
3. La expiracion puede apoyarse en workers o jobs programados
4. La lectura puede cachearse

Ejemplo de datos de historia:

- id
- autor_id
- media_url
- tipo_media
- fecha_creacion
- fecha_expiracion
- estado

Que deberia pasar tecnicamente:

- el backend registra la historia
- el archivo se guarda fuera del servidor
- un worker o tarea programada limpia o desactiva historias expiradas
- el frontend consulta historias activas

Por que no necesitas NoSQL solo por esto:

- la logica de historia sigue siendo relacional
- el volumen fuerte esta en la media y en la lectura, no solo en la fila SQL


========================================================================
16. LIKES: PARECEN SIMPLES, PERO TIENEN DETALLES IMPORTANTES
========================================================================

Un like parece una operacion pequeña, pero en sistemas grandes se convierte
en una fuente masiva de lectura y escritura.

Que necesitas controlar:

- evitar likes duplicados
- contar likes rapido
- saber si el usuario actual ya dio like
- actualizar interfaces en tiempo real o casi real

Modelo relacional base:

Tabla LIKES_POST:
- id
- usuario_id
- post_id
- fecha_creacion

Constraint importante:

- unique(usuario_id, post_id)

Eso evita duplicados.

Que problema aparece luego:

- contar likes en cada lectura puede costar si no hay estrategia

Soluciones:

- mantener conteos derivados
- cachear conteos en Redis
- recalcular o sincronizar con jobs

NoSQL puede ayudar en algunos patrones, pero no es obligatorio para empezar.

Para TeleRin lo correcto seria:

- guardar el like verdadero en PostgreSQL
- usar cache o contadores derivados si la lectura crece mucho

17. COMENTARIOS: POR QUE SIGUEN SIENDO MUY BUEN CASO PARA SQL
========================================================================

Los comentarios encajan naturalmente en SQL porque:

- tienen autor
- pertenecen a un recurso
- tienen fecha
- pueden tener moderacion
- pueden ordenarse
- pueden paginarse

Datos tipicos:

- id
- post_id
- autor_id
- texto
- fecha_creacion
- estado_moderacion

Que problemas reales aparecen:

- paginacion
- comentarios muy numerosos
- orden cronologico o destacado
- moderacion

Todo eso puede manejarse perfectamente con PostgreSQL, indices y paginacion
correcta.


========================================================================
18. INDICES: LA DIFERENCIA ENTRE UNA APP RAPIDA Y UNA APP QUE SUFRE
========================================================================

Un indice en base de datos es una estructura que acelera busquedas.

Por que importa:

- sin indices, una tabla grande se vuelve lenta
- con indices correctos, consultas muy frecuentes vuelan

Ejemplos de indices utiles para TeleRin:

USUARIOS:
- indice por username
- indice por email

POSTS:
- indice por autor_id
- indice por fecha_creacion
- indice compuesto por autor_id y fecha_creacion

HISTORIAS:
- indice por autor_id
- indice por fecha_expiracion

COMENTARIOS:
- indice por post_id y fecha_creacion

LIKES:
- indice por post_id
- indice por usuario_id
- unique por usuario_id y post_id

Que pasa si no piensas esto desde ya:

- el crecimiento te castiga con consultas lentas
- el feed se degrada
- perfiles tardan en cargar
- los listados se vuelven caros

En que parte lo vas viendo:

- en las migraciones
- en EXPLAIN ANALYZE
- en tiempos de respuesta


========================================================================
19. REPLICAS DE LECTURA: CUANDO IMPORTAN
========================================================================

Una replica de lectura es una copia de la base principal que recibe datos
replicados y se usa para consultas.

Por que sirven:

- descargas la base principal
- separas lecturas de escrituras
- escalas consultas frecuentes

Ejemplo:

- PostgreSQL principal recibe inserts, updates y deletes
- una o varias replicas atienden consultas de feed, perfiles o listados

Para TeleRin, esto importa cuando:

- hay muchisimas mas lecturas que escrituras
- la base principal empieza a saturarse

No suele ser lo primero que implementas, pero si deberias saber que tu
diseño debe permitirlo.


========================================================================
20. PARTICIONADO Y SHARDING: NO SON LO MISMO
========================================================================

Particionado:

- dividir una tabla grande en partes lógicas
- por ejemplo, por fecha o por rango de ids

Sharding:

- repartir datos entre distintas bases o nodos

Por que importa entender la diferencia:

- mucha gente habla de sharding demasiado pronto
- a veces el problema real se resuelve antes con indices, cache y replicas

Ejemplo de particionado util en TeleRin:

- historias por fecha
- eventos o logs por mes
- actividad por rango temporal

El particionado ayuda cuando:

- las tablas crecen mucho
- consultas por rango temporal son frecuentes

Sharding se vuelve relevante bastante despues, cuando:

- una sola base ya no es suficiente
- el volumen es extremo
- tienes equipos y operacion mucho mas maduros


========================================================================
21. AUTENTICACION Y GESTION DE SESIONES
========================================================================

La autenticacion no solo consiste en validar usuario y contrasena.

Tambien implica:

- proteger sesiones
- rotar secretos
- controlar expiraciones
- limitar abuso
- guardar informacion sensible correctamente

Que deberia tener TeleRin:

- contrasenas hasheadas con algoritmos adecuados
- secretos fuera del codigo fuente
- sesiones o tokens con expiracion
- revocacion o invalidacion cuando sea necesario
- rate limiting en login
- proteccion ante bots y abuso

Donde deberias verlo:

- backend
- variables de entorno
- almacenamiento de sesion
- politicas de seguridad

Importante:

Si el proyecto quiere muchas instancias, las sesiones no deberian depender
de memoria local del proceso.

Redis es muy util aqui.


========================================================================
22. SECRETOS Y CONFIGURACION
========================================================================

Un secreto es cualquier dato sensible como:

- claves de sesion
- passwords de base de datos
- tokens de terceros
- claves de correo
- secretos JWT

Por que no deberian vivir en el codigo:

- se filtran facil
- complican rotacion
- mezclan configuracion con logica
- son riesgo de seguridad

Lo correcto:

- variables de entorno
- secret managers en produccion

En que parte lo verias:

- Docker
- archivos de entorno
- configuracion de despliegue

Por que deberia estar bien desde ya:

- corregir seguridad tarde es mucho mas doloroso


========================================================================
23. LOGS, METRICAS Y OBSERVABILIDAD
========================================================================

Observabilidad es la capacidad de entender que esta pasando en tu sistema.

Sin observabilidad, cuando algo va mal:

- no sabes donde
- no sabes por que
- no sabes si es base de datos, red, backend o cache

Componentes principales:

1. Logs
   Registros de eventos del sistema.

2. Metricas
   Numeros agregados sobre salud y rendimiento.

3. Tracing
   Seguimiento de una peticion a traves de varios componentes.

Que deberias medir en TeleRin:

- tiempo de respuesta por endpoint
- errores 4xx y 5xx
- uso de CPU y memoria
- cantidad de conexiones a base de datos
- hit rate de cache
- tiempo de queries
- volumen de jobs pendientes

Herramientas comunes:

- Sentry para errores
- Prometheus para metricas
- Grafana para dashboards
- OpenTelemetry para tracing

Por que esto deberia estar:

- porque una app grande no se administra a ciegas


========================================================================
24. RATE LIMITING Y PROTECCION CONTRA ABUSO
========================================================================

Una red social publica enfrenta abuso.

Ejemplos:

- spam de comentarios
- ataques de login
- scraping agresivo
- likes automatizados
- creacion masiva de cuentas

Rate limiting significa limitar cuantas acciones puede hacer un cliente en
cierto tiempo.

Ejemplos:

- maximo N logins por minuto por IP
- maximo N comentarios por minuto por usuario
- maximo N likes por minuto

Redis es excelente para esto porque maneja:

- contadores rapidos
- expiraciones por ventana de tiempo

Por que deberia estar en TeleRin:

- no solo por seguridad
- tambien por estabilidad operativa

25. MODULARIDAD DEL CODIGO: POR QUE IMPORTA TANTO
========================================================================

Un archivo grande unico puede funcionar al inicio, pero se vuelve dificil
de mantener a medida que crece.

Problemas de un backend demasiado concentrado:

- cuesta entender responsabilidades
- cuesta probar
- cuesta aislar errores
- cuesta reemplazar piezas
- varios desarrolladores chocan mas

Como deberia verse una estructura mas madura:

- modulo de autenticacion
- modulo de usuarios
- modulo de publicaciones
- modulo de comentarios
- modulo de historias
- modulo de media
- modulo de notificaciones
- modulo de acceso a datos
- modulo de configuracion

Por que esto ayuda a escalar:

- facilita evolucionar a servicios separados si algun dia hace falta
- reduce complejidad accidental


========================================================================
26. MIGRACIONES DE BASE DE DATOS
========================================================================

Una migracion es una forma controlada de cambiar el esquema de la base.

Ejemplos:

- crear tabla nueva
- agregar columna
- crear indice
- cambiar constraint

Por que importan:

- hacen reproducibles los cambios
- permiten desplegar con orden
- reducen errores manuales

En un proyecto serio, no deberias depender de:

- "yo cree esa tabla a mano"
- "agrega esa columna directo en pgAdmin"

Para TeleRin, esto deberia existir si el sistema va en serio.


========================================================================
27. API Y PAGINACION
========================================================================

La paginacion es vital en cualquier sistema con listas grandes.

Listas tipicas en TeleRin:

- posts del feed
- comentarios
- seguidores
- seguidos
- historias activas
- notificaciones

Por que no debes devolver todo:

- respuestas pesadas
- alto consumo de memoria
- mala experiencia de red
- mas carga en base de datos

Tipos de paginacion:

- offset/limit
- cursor-based pagination

Para crecer bien, cursor-based suele escalar mejor en listas grandes.

Ejemplo:

En vez de pedir:
- dame todos los comentarios del post

Pides:
- dame los siguientes 20 comentarios despues de este cursor


========================================================================
28. BUSQUEDA: CUANDO ENTRA UN MOTOR ESPECIALIZADO
========================================================================

Buscar no es lo mismo que guardar.

Una base transaccional puede buscar cosas simples, pero si luego quieres:

- busqueda por texto
- relevancia
- typo tolerance
- filtros complejos

entonces puede convenir un motor dedicado.

Ejemplos:

- Elasticsearch
- OpenSearch

Para TeleRin, esto importa si algun dia quieres:

- buscar usuarios
- buscar hashtags
- buscar posts por contenido

No hace falta de entrada, pero si conviene entender que es un componente
distinto al almacenamiento principal.

29. NOTIFICACIONES
========================================================================

Las notificaciones pueden ser:

- in-app
- push
- email

Eventos tipicos:

- alguien dio like
- alguien comento
- alguien siguio a otro usuario
- alguien respondio comentario

Por que deberian pasar por cola:

Como se veria:

- backend o servicio de push la entrega


========================================================================
30. REALTIME: CUANDO REALMENTE HACE FALTA
========================================================================

No todo necesita tiempo real desde el dia uno.

Tiempo real puede significar:

- websockets
- server-sent events
- polling corto

Casos donde aporta:

- chat
- notificaciones instantaneas
- indicadores de actividad
- actualizacion de conteos en vivo

Casos donde puede esperar:

- likes que se reflejan al recargar
- conteos que se actualizan con polling

Por que no deberias meter complejidad realtime sin motivo:

- agrega dificultad operativa
- agrega manejo de conexiones persistentes
- cambia escalado


========================================================================
31. PROCESAMIENTO DE MEDIA
========================================================================

Media no es solo "subir archivo".

Puede incluir:

- validacion de tipo
- validacion de peso
- compresion
- thumbnails
- varias resoluciones
- metadata
- moderacion

Todo eso deberia pasar fuera del request principal o al menos minimizarse.

Ejemplo en TeleRin:

Usuario sube foto para historia.

Pipeline ideal:

1. backend recibe archivo
2. valida lo basico
3. guarda temporal o sube a storage
4. crea tarea de procesamiento
5. worker genera versiones
6. se actualiza metadata final

32. MODELO DE DATOS: COMO PENSARLO DESDE AHORA

Pensar modelo de datos no es solo crear tablas. Es decidir:

- que consultas vas a hacer mas seguido
- que datos crecen mucho
- que datos expiran

En TeleRin, deberias pensar claramente en dominios:

- identidad

- follows

Contenido:
- posts

Media:

Actividad:

Esto importa porque luego:

- separas servicios mas facilmente


========================================================================
33. EJEMPLO DE FLUJO COMPLETO: CREAR UNA PUBLICACION
========================================================================

Veamos como se veria un flujo bien pensado.

Caso:
- usuario publica una foto con texto

Flujo:

1. Cliente envia request al backend
   Incluye token o sesion y el contenido.

2. Backend valida autenticacion
   Revisa identidad del usuario.

3. Backend valida el archivo y el texto
   Tamaño, tipo y reglas de negocio.

4. Backend guarda metadata inicial de la publicacion
   En PostgreSQL.

5. Backend manda archivo a object storage
   O gestiona upload directo si el flujo se diseña asi.

6. Backend encola tarea de procesamiento de media
   Worker genera tamaños y derivadas.

7. Backend responde rapido al cliente
   Confirmando que la publicacion fue aceptada.

8. Worker procesa la imagen
   Genera variantes y actualiza metadata.

9. Worker o pipeline actualiza caches o feed
   Si aplica.

10. CDN sirve la imagen a los demas usuarios
    Sin cargar al backend principal.

Eso es mucho mas escalable que:

- guardar imagen en disco local
- hacer todo en el request
- servir la imagen desde Flask


========================================================================
34. EJEMPLO DE FLUJO COMPLETO: DAR LIKE
========================================================================

Caso:
- usuario da like a una publicacion

Flujo:

1. Cliente envia accion
2. Backend valida autenticacion
3. Backend inserta like en PostgreSQL
4. Constraint evita duplicado
5. Backend actualiza o invalida cache del contador
6. Worker opcional genera notificacion
7. Cliente recibe respuesta rapida

Posibles mejoras futuras:

- contadores derivados
- notificacion asincrona
- actualizacion realtime si existiera websocket


========================================================================
35. EJEMPLO DE FLUJO COMPLETO: VER FEED
========================================================================

Caso:
- usuario abre inicio

Flujo recomendado:

1. Backend identifica usuario
2. Consulta cache de feed en Redis
3. Si existe, devuelve resultados
4. Si no existe, consulta PostgreSQL
5. Arma feed con paginacion
6. Guarda resultado temporal en Redis
7. Devuelve respuesta

Problema si no haces esto bien:

- cada apertura de inicio castiga duramente la base

36. CUANDO TENDRIA SENTIDO UN SERVICIO SEPARADO

Separar servicios demasiado pronto puede:

- complicar despliegues
- multiplicar debugging
- aumentar latencia interna

Regla sana:

- primero modular dentro del monolito
- luego extraer si un dominio ya lo justifica

40. RESPUESTA DIRECTA A TU DUDA DE FONDO
========================================================================

Si tu pregunta de fondo es:

"Si quiero millones de usuarios, que deberia tener ya, y deberia usar otros
lenguajes mas rapidos o mas potentes?"

La respuesta tecnica madura es:

Deberias tener ya:

- una base de datos principal seria como PostgreSQL
- un diseño de datos correcto
- pensamiento modular
- preparacion para Redis
- preparacion para object storage
- preparacion para CDN
- preparacion para workers
- API stateless
- seguridad y configuracion bien hechas

No deberias obsesionarte ya con:

- reescribir todo en otro lenguaje
- meter microservicios demasiado pronto
- usar NoSQL sin un problema concreto que resolver

Si algun dia una parte concreta de TeleRin necesita un lenguaje mas rapido,
se puede mover esa parte sin destruir todo el sistema.

La verdadera fortaleza no esta en elegir la tecnologia "mas poderosa" en
abstracto. La verdadera fortaleza esta en construir un sistema donde cada
pieza tenga una responsabilidad clara y pueda evolucionar sin romper las
demas.

41. CIERRE
========================================================================

TeleRin puede aspirar a una arquitectura muy seria sin abandonar Python de
inmediato. Lo mas importante es no confundir escala con moda tecnologica.

Las plataformas grandes no son fuertes solo por usar cierto lenguaje o
cierta base de datos. Son fuertes porque:

- separan responsabilidades
- usan almacenamiento correcto para cada tipo de dato
- reducen trabajo dentro del request
- miden todo
- cachean lo necesario
- escalan horizontalmente
- sirven media eficientemente

Si TeleRin se construye con esa mentalidad, entonces el proyecto puede
crecer muchisimo mejor que si simplemente cambia de stack sin estrategia.
